# 布局范式（layout recipes）

每种布局给出「什么时候用 + 节点/边怎么组织」。

## flow-v / flow-h（分层流程）

- 什么时候用：有明确先后顺序的步骤、审批链、因果链、管道。
- 组织方式：
  - 按"层"组织节点：起点层 → 处理层 → 终点层；边尽量只连相邻层（跨层边会导致排版松散）；
  - 判断分支：判断节点用 `diamond`，两条出边各带 `label`（是/否）；分支合并后继续流向下一层；
  - 起点用 `rounded + tone:start`，终点用 `rounded + tone:end`；
  - 节点名长的图用 `flow-h`（横排），短名词用 `flow-v`（竖排）。
- 反例：不要把 20 个节点塞进一条链，拆成 2~3 张图或用分组收纳。

## mindmap（思维导图）

- 什么时候用：总分结构、层级展开、头脑风暴、知识整理。
- 组织方式：
  - 第一个节点 = 根（中心主题），边定义父子关系（from=父, to=子）；
  - 只保留树形边，不要画交叉引用；同层兄弟 ≤ 8 个；
  - 层级 ≤ 3（根 → 一级 → 二级），更深的层级建议拆图；
  - 一级节点用 `tone: highlight` 区分主题分支。

## swimlane（泳道）

- 什么时候用：多角色/多系统协作，需要体现「谁做什么」。
- 组织方式：
  - 每个 group = 一条泳道（角色/系统名放 label）；
  - 节点放进对应角色的 group；泳道内部按流程走向排布（系统会横向分层）；
  - 跨泳道的边表示职责交接，建议带 `label`（交付物或动作）；
  - 不属于任何 group 的节点会落到「其他」泳道，尽量避免。

## sequence（时序）

- 什么时候用：对象之间的消息交互顺序（接口调用、协议交互）。
- 组织方式：
  - nodes = 参与者（按交互顺序排列，第一个通常是用户/发起方），参与者用 `rounded`；
  - edges = 消息，**按时间顺序**排列（每条边占一行，从上往下）；
  - `label` = 消息名（动作短语）；返回/异步响应用 `kind: dashed`；
  - 消息 ≤ 12 条，超过建议拆成多个阶段两张图。

## 分组容器（非 swimlane 的 groups）

flow-v / flow-h / mindmap 也可以带 groups：系统会按子节点包围盒画背景框。
适合「阶段一/阶段二」这类阶段框，或「前端/后端」这类子系统框。
